# 目标队列：自进化系统在"没事干"时的燃料

> 来源：用户 2026-09-28 夜的一句话。
> 当时一个本地 agent 框架刚被启动，没有任何任务在跑，GPU 利用率 0%。
>
> **「自进化的前提是永生，永续，得不断的迭代升级，但会面临不知道干嘛的时候，**
> **那就是应该有一堆任务目标，按层次，按先后，但前提是有无限的 Tokens，**
> **把我们设备与电力尽量的用。」**

---

## 一、自进化系统的真实失效模式不是崩溃，是**空转**

**这一点在写这份文档的一小时前被亲手演示了：**

```
22:2x  启动那个框架              launch.pyw ×2, stapp.py ×2 起来了
22:17  停用唯一的调度任务          理由：深化已完成，任务失去对象
22:3x  状态
         任务队列      一个条目，enabled=False
         进程          活着，零活动
         GPU           4265 / 16303 MiB，利用率 0%
         Ollama        一个模型都没加载
```

**★ 系统没有坏。它只是**没有下一步**。**

**★★ 而这正是用户预判的形态：**
> **「会面临不知道干嘛的时候」**

**★★★ 所以 dsh-steward 的第一条设计前提要改：**

| 原设计 | 修正 |
|---|---|
| 触发器是**检查失败** | 触发器是**检查失败 OR 队列非空** |
| 没事时系统静止 | 没事时系统**从队列取下一件事** |
| 空转 = 正常 | **空转 = 缺陷**（有算力而不用） |

## 二、GA 有什么、缺什么

### 有的（比预想的完整）

```
goal_mode_sop.md      开放目标 + 时间预算
                      temp/goal_state.json:
                        { objective, budget_seconds, start_time,
                          turns_used, max_turns, status }
                      ★ SOP 里举的例子就包括「没事也找事干」

goal_hive_sop.md      Goal Mode 的多 worker 协议
                      · BBS（本地端口 + API key）作任务板
                      · Hive Master ——「负责任务调度和团队组织，
                        不允许亲自干活导致 worker 空转」
                      · Worker 2–4 个（上限 5）
                      · 第一帖规范要求写死一句：
                        「此为最终目标，worker不要接单，先等 hive master 拆分子任务。」

goal_hive_master_duty.md   master 的职责清单
incubator_sop.md           孵化
```

**★★ 所以：目标执行器、多 worker 协作、master/worker 分工、任务板 —— 全都有。**

### 缺的

| # | 缺什么 | 后果 |
|---|---|---|
| 1 | **持久的目标池** —— `goal_state.json` 每次运行现建，`budget_seconds` 用尽即停 | 预算一完就空转 |
| 2 | **层次与先后** —— 没有"什么必须优先"的概念 | 可能在做 L4 探索时 L0 已经坏了 |
| 3 | **空闲检测** —— 没有任何东西发现"系统闲着" | 0% 利用率可以持续几天无人知 |
| 4 | **目标供给** —— 目标永远来自用户当下的一句话 | 用户不说话 = 系统停摆 |

**★★★ 一句话：GA 有目标的跑步机，没有目标的仓库。**

## 三、目标队列的设计

### 3.1 分五层，L0 最高

```
L0  存活       dsh 能起来吗 · 备份能还原吗 · 凭据安全吗
               ★ 唯一一条可以【打断一切】的层

L1  一致       数据/记忆/索引自洽吗
               vecmem 的 items↔rows · 备份链完整 · 索引与源同步

L2  已知缺口    已经发现、还没修的
               3 个 cordis backport 补丁 · GA 规格里那几条可抄的

L3  能力扩展    新东西
               空间数据项目 Layer 3–7 · 新插件 · 新 IM 适配器

L4  探索        调研、外部项目、新想法
               四路 GA 考古 · 别家的自进化实现
```

### 3.2 先后规则

```
L0 非空  →  只做 L0，其余全部暂停
L0 空、L1 非空  →  L1 优先，L2 可并行
L0/L1 都空      →  L2 优先，L3 可并行
L0–L2 都空      →  ★ L3/L4 是供给源 —— 这才是"自进化"真正发生的地方
```

**★ 关键性质：只要 L3/L4 永远非空，系统就**永远不会没有下一步**。**

**★★ 而 L3/L4 是最容易保持非空的层 —— 因为"还能做什么"是个开放集合，而"必须修什么"是个有限集合。**

### 3.3 每条目标的格式

**★★ 从今晚的失败里学到的（见 `GA-FAILURE-CASES.zh.md`）：**

```yaml
id:           唯一标识
layer:        L0..L4
objective:    一句话
evidence:     ★ 怎么知道它还没做完 —— 必须是一个【可执行的检查】
              「len(items) == len(rows)」而不是「检查一致性」
verify:       ★ 完成后怎么证明 —— 同样必须可执行
rollback:     做砸了怎么退
budget:       预计多少轮 / 多少秒
blocked_by:   依赖哪些前置
```

**★★★ `evidence` 和 `verify` 必须是**可执行的**，这是唯一的硬性要求。**

**理由就是今晚那条：**

> **它能核对的（有备份可比对）→ 全对**
> **它只能靠阅读判断的 → 全错**
> **而两者在输出里长得一模一样**

**所以目标不能写成"提升数据质量"，要写成"`keytag` 过滤后重算 Layer 5，与旧分数逐条比对，差异分布落在预定区间内"。**

## 四、"无限的 Tokens，用尽设备与电力"

**用户这句话有两层：**

### 4.1 字面层：本机算力在闲着

```
RTX 5080        16,303 MiB 总量 · 4,265 MiB 已用 · 利用率 0%
Ollama          6 个模型 · 当前加载 0 个
~250 GB 权重    unsloth/GLM-5.3-Flash-GGUF 92 GB
                Qwen3.8-Flash-Next-GGUF 69 GB
                Qwen3.8-27B-GGUF 18 GB
                DeepSeek-V3.1-GGUF …
```

**★ 所以"用尽设备与电力"在物理上是可执行的 —— 不是修辞。**

### 4.2 ★★★ 结构层：这决定了系统能不能**自己转起来**

| | 依赖外部 API | 用本机算力 |
|---|---|---|
| 有配额时 | 能做 | 能做 |
| 配额用完 | **停** | 继续 |
| 网络断 | **停** | 继续 |
| 被掐 | **停** | 继续 |

**★★ 而用户的整个目标是"摆脱被掐"。所以：**

> **一个依赖外部 API 才能空转的自进化系统，在被掐的那一刻就死了。**
> **本机算力不是"省钱"，是【永生】的物质基础。**

**★★★ 这直接改变了 dsh-steward 的架构约束：**

```
能离线做的（L0 检查、L1 一致性、本地索引、文档处理）  →  用本机模型，永久可跑
必须在线做的（外部 API 调用、外部资料）              →  有配额时做，没配额时排队
```

**★★★★ 而"按层次、按先后"在这里有了第二个含义：**
**不只是优先级，还是**能不能离线**。L0/L1 必须能离线跑 —— 因为 dsh 起不来的时候，可能连网都没有。**

## 五、这与已有的三条支柱、四条约束的关系

**★ 目标队列不是第四条支柱，是让前三条**持续运转**的机制。**

```
三根支柱（何时可信）
  ① 可执行的外部反馈
  ② 不可被改动的评测
  ③ 能退回的存档

目标队列（做什么）
  L0–L4 分层，永远非空

四条约束（不许做什么）
  ① 检查必须被坏输入证伪过
  ② 改动前必须有基线
  ③ 监督者先报告后动手
  ④ 永不进入第三层
```

**★★ 而今晚新加的两条：**

```
⑤ ★ 报告里的每个数字必须带产生它的命令
     （来源：GA 把 14,039 说成 14,040）

⑥ ★ 任何基于观测的结论，必须声明它假设了什么没有变
     （来源：用户关于物理世界漂移的那段话）
```

**★★★ 加上目标队列本身带来的第七条：**

```
⑦ ★ 空转是缺陷，不是静止
     有算力而不用 = 系统在退化（因为物理世界还在变，而它没在看）
```

## 六、最小可执行的形态

**★ 不要一上来就做 BBS + master + worker。第一版只需要：**

```
goals/
  L0-survival.yaml
  L1-integrity.yaml
  L2-known-gaps.yaml
  L3-expansion.yaml
  L4-exploration.yaml

每层一个文件，里面是一个列表。
每条目标带 evidence（可执行检查）和 verify（可执行验证）。

systemd timer（每 15 分钟）:
  1. 跑 L0 的 evidence —— 任何一条失败 → 通知人，停
  2. L0 全过 → 跑 L1 的 evidence —— 有失败 → 通知人
  3. L0/L1 全过 → 从 L2 取第一条未完成的 → ★ 报告"下一件该做的"
     （第一版只报告，不动手 —— 见约束③）

★ 而 L3/L4 的条目由【人】和【agent】共同维护，
  每次会话结束时把"还能做什么"追加进去。
```

**★★ 关键：第一版**只报告，不动手**。它解决的是"不知道干嘛" —— 而"知道了之后谁去做"是另一个问题。**

**★★★ 这也符合已有的约束③：监督者先报告后动手。**

## 七、一句话

**用户那句话可以压成一个判据：**

> **一个自进化系统，在任何时刻都应该能回答："下一件该做的是什么，为什么是它，怎么知道做完了。"**
>
> **答不出来，它就不是在自进化 —— 它只是在等指令。**

**★ 当时那个系统答不出来。它的队列是空的，GPU 是 0%，而它自己是活的。**
