## 一、改变设计的七条

按「会改多少」排序。

### 1. ★★★ 差分运行器不是我们发明的，是搬来的

**报告 1 问「AGREE/DIVERGE 没有先例」，它猜对了圈子。**

```
McKeeman 1998 · "Differential Testing for Software"
Ada Conformity Assessment Test Suite (ACVC)     航空/军工的编译器适航验证
GCC / LLVM / ICC 交叉测试                        编译器圈标准实践
```

**核心洞见：不需要 oracle，只需要两个实现。**

**改什么**：README §3.1 现在的写法像是我们的设计。应改为「**搬来的**，而搬来这件事本身值得记 —— 它意味着 agent 圈在这件事上落后传统工程二十年」。

---

### 2. ★★★ 我昨晚那两个事故，是 bash 的**默认行为**，不是倒霉

**报告 3 把它们变成了可机器化的规则：**

```
① a && b || c 永远返回 0
   Bash 手册: "The return status of AND and OR lists is the exit status
              of the last command executed in the list."
   → 我昨晚的 `test -w file && echo writable || echo readonly` 就是这个形状

② 任何 evidence 里出现【无条件成功的命令】（echo / true / cat / printf）
   → 那个检查就是空的
   ★ 而这条可以机器化检查
```

**改什么**：`steward.mjs` 应加一个**自检**：遍历所有 `goals/L*.json` 的 evidence，命中无条件成功命令就报错。**这是把昨晚的事故变成永不复发。**

---

### 3. ★★ 短消息的解法有先例，而我们的设计方向对了 —— 但有一个陷阱

**报告 2 的结论：**

```
两家（mem0 / Letta）立场一致：短消息不进长期记忆层
三家（MemoryOS / Graphiti / Letta）同一个工程结论：
  ★ 短消息的检索单元不能是短消息本身
  MemoryOS  装 QA 对 → 晋升成 page → pre_page/next_page 连成链
  Graphiti  Episode + NextEpisodeEdge + episode_mentions 重排器
  Letta     按时间窗捞，绕开语义检索
```

**我们的 L2.1「逐条 + 节奏聚合」正落在第二类上。方向对。**

**★★ 但陷阱在这：**

```
mem0 的 score_and_rank() 里 threshold 在【融合之前】生效
→ 短消息对任何 query 的向量分都低
→ 即使 BM25 或实体图能命中，也永远进不了候选集

★★★ 对我们的两阶段检索（嵌入余弦 → top-50 → 重排）：
    如果短消息在第一阶段被截掉，重排再强也没用
```

**改什么**：`rerank-search.mjs` 的第一阶段候选集，**不能只按余弦分排序** —— 必须给 `meta.kind === "short-turn"` 的条目留配额，或者把节奏条目（它分数高，因为成串）作为短消息的入口。

---

### 4. ★★ 三次真实案例：检查骗过了所有人

**报告 3 §5 的 17 条里，三条与本仓直接同型：**

| 案例 | 声称验证了什么 | 实际验证了什么 |
|---|---|---|
| **本仓 evidence 的 echo** | 文件可写 | 印了一行字 |
| **SWE-bench `grading.py:29-31`** | 套件跑过 | 空状态表 + FAIL_ONLY ⇒ **每个 F2P 都算通过** |
| **SWE-bench `grading.py:164-176`** | 测试通过 | 补丁可以自己 `print("PASSED")` |

**★ 而报告 1 又给了一条反例：**

```
SWE-bench compute_fail_to_pass() 在 total == 0 时 return 1
→ ★「没有用例」被当成满分
→ 与上面第一条方向相反，抄结构时必须【反过来写】
```

**改什么**：六条不变量里应加一条 **`I0.no-vacuous-pass`** —— 任何检查在"没有输入"时必须报 FAIL 或 INCONCLUSIVE，**不能报 PASS**。

---

### 5. ★★ 我们的 timer 有两个静默失效模式

**报告 4 实测：**

```
#3  timer 到点时如果目标 unit 还是 active，systemd 静默跳过，不报错
    → 只要上一次没退出，定时器就永远空转
    ★★ 我刚给 dsh-steward 接了 timer —— 如果 steward.mjs 卡住，没人知道

#5  OnCalendar 的区间+重复 = 窄窗口
    [实测] 08..20/6 → 08:00/14:00/20:00，之后 12 小时空窗
    ★ 这是 GenericAgent 那个 every_Nh bug 的 systemd 版本

#6  AccuracySec 默认 1min、RandomizedDelaySec 每次迭代重新随机
    →「每小时」不等于「整点」
```

**改什么**：
- 给 timer 加 **`RuntimeMaxSec=`**（跑太久就杀）
- 给 service 加 **`WatchdogSec=`**（活着但无进展也杀）
- 每次运行**写一份可检验的执行记录**，让"静默跳过"变成可见

---

### 6. ★★ 重启杀死在飞队员 —— 有机制解释，也有正确做法

**报告 4 §5.3 用 `systemd.kill(5)` 解释了我昨晚的误杀：**

```
KillMode=control-group 是【默认值】
→ 停止一个 unit = 杀掉它的整个 cgroup
→ dsh 重启 = 杀掉 dsh 的 cgroup 里所有进程
   ★ 包括它 spawn 的队员 —— 除非它们在【另一个 cgroup（另一个 unit）】里
```

**改什么**：
- 长任务用 `systemd-run --user` 起**独立 unit**，让重启不影响它
- 或者：**先落盘，再深挖** —— 报告 4 的原话是「这不是风格问题，是中断损失上界问题」

---

### 7. ★ 五种"防跑飞"机制，我们只有一种

**报告 1 的清单（每条带出处），我们对照：**

| 机制 | 谁在用 | dsh-steward |
|---|---|---|
| 容器隔离 | DGM | ✗ |
| 单次执行时限 | DGM（两层：容器内 1800s + 外层 1.5h） | ✗ |
| 自改范围限定在 agent 代码库 | DGM | ✓（§4.4 永不进入第三层） |
| 归档可追溯 | DGM | ✓（git + 备份） |
| ★ **版本级验证（改完新起实例跑真实任务）** | SICA | ★ **计划中，未实现** |
| ★ **置信区间下界选版本** | SICA `runner.py:88-150` | ✗ |

**★★ 而报告 1 指出最要害的一格：**

> **SICA 把「版本级验证」这一步留给了人**（主语是 "you must inspect"）
> **—— 那正是 dsh-steward 要换掉的一格。**

**★★★ 而 SICA 的选版本机制值得直接抄：**

```
不追点估计最高分，而是【在噪声带内挑最新的】：
  算每个迭代的 CI → 取最好的那个的 ci_lower
  → 从当前迭代【往前回扫】，返回第一个 mean >= best_ci_lower 的迭代
```

## 二、改变看法的三条

### 8. ★★★ 昇腾的问题不是「弱」，是「不卖给你」

```
个人能买到的两极：
  Atlas 200I DK A2    8T / 4GB        边缘套件
  Atlas 350 (950PR)   600W · 8卡 · 6U  整机

★ 中间那层 —— 单张能插桌面机、跑得动大模型的卡 —— 找不到可零售证据
```

**而 CANN 已完整开源**（82 仓 / 31.78K star / 66.81M 下载，含算子库、通信库、图引擎、运行时、**驱动**）。

**改什么**：README §8「单机做不到的」应加一条 —— **算力自主的瓶颈不在软件栈，在零售渠道**。

### 9. ★★ 国产 API 在集体涨价，这**支持**「本地权重优先」

```
DeepSeek V4-Flash 输出  2 → 9 元/百万 token（+350%，2026-08-17）
智谱年内三次涨价 · Kimi K3 输出 100 元/百万（较 K2.6 涨 3-4 倍）
高盛口径：中国大模型平均输出价 12.2 → 21.9 元（+80%）
```

**报告 5 的判语：**

> **涨价恰恰证明把命脉放在别人 API 上，定价权不在你手里。**
> **这让「本地权重」的价值不只是省钱，而是自主性。**

**★ 而本机实测：** 160.3 GB 国产权重（GLM-5.3-Flash 91.9 + Qwen3.8-Flash-Next 68.4）**下载了但一个都没注册进 Ollama**。

### 10. ★ 硬墙四条（不是难度问题）

```
Linux 上做 HarmonyOS 开发     官方只有 Windows/macOS，无 Linux 版
16GB 全 GPU 跑 27B Q4        ★ 实测 15.92 GiB 显存 vs 16.52 GiB 权重，超 0.60
RISC-V 跑混合 SSM 模型        掉到 1–3.5 tok/s，benchmark 直接写 avoid
昇腾迁移                      官方 180 页指南逐条列出不支持项
```

## 三、诚实清单：五路都没找到答案的

**这些不该被"综合"掩盖。**

```
1. 编号不变量清单没有先例 —— 只有 SWE-bench 的 F2P/P2P 二元结构
2. ShinkaEvolve 的回退实现、live-swe-agent 的工具跨轮复用、agent-zero 的验证路径
3. 昇腾迁移成功率官方从未公布 —— ★ 任何百分比都不要采信
4. 高德/百度/腾讯官方免费配额数字 —— 官方页是 JS SPA，取不到正文
   ★ 报告 5 明确写「我拒绝编造数字」
5. Trae/CodeBuddy 等的本地模型支持与定价
6. DGM is_compiled_self_improve 判定细节、openevolve _cascade_evaluate 函数体
7. 锚定：Anthropic contextual retrieval / late chunking / 会话式查询改写
   —— 报告 2 标为"本任务价值最高的缺口"
```

**★★ 报告 5 有 21 项标成 ✗，它写的是「不是没查到，是没有依据所以不下结论」。**
